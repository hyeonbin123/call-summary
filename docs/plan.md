# 개발 계획 (2026-09-26, 개발 시작 전)

## 목표
고객센터 상담 대화(텍스트 전사)를 받아 **상담 후처리 기록**(요약, 문의 유형, 처리 결과, 후속 조치, 주문번호·금액 같은 핵심 값)을 정해진 JSON으로 뽑는 소형 LLM(약 2~4B)을 LoRA/QLoRA로 학습하고, 로컬에서 서빙한다. 학습 전후와 큰 모델 대비 성능을 **미리 정한 규칙으로** 측정한다.

## 측정으로 답할 질문
1. 2~4B 모델을 이 작업에 맞게 학습하면, 학습하지 않은 7B·14B 모델과 비교해 어디까지 따라가는가 (필드 정확도, 핵심 값 정확도, 요약 사실 포함률)
2. 학습으로 가장 크게 좋아지는 것은 무엇인가: JSON 형식 준수, 유형 분류, 핵심 값 추출, 요약. 그리고 **대화에 없는 값을 지어내는 비율**은 줄어드는가 늘어나는가
3. 학습 데이터를 만든 생성기와 다른 방식으로 만든 대화, 학습에 없던 업종의 대화에서도 이득이 남는가 (생성기 차이 / 도메인 차이)
4. 음성 인식 오류가 섞인 전사(TTS → STT로 만든 조건)에서는 얼마나 떨어지는가. 깨끗한 전사로만 학습한 것과 인식 오류를 섞어 학습한 것은 다른가
5. 양자화(GGUF Q8/Q4)로 줄였을 때 정확도를 얼마나 잃고, 지연 시간과 메모리는 얼마나 얻는가

## 과제 정의: 상담 후처리 기록
입력은 상담원·고객 발화가 번갈아 나오는 대화 전사. 출력은 아래 스키마의 JSON 하나 (pydantic으로 정의하고 검증한다. 확정은 0단계).

| 필드 | 형태 | 채점 |
|---|---|---|
| `category` | 정해진 문의 유형 중 하나 (업종별 8~12개) | 정확도, macro-F1 |
| `resolution` | 해결 / 부분 해결 / 미해결 / 이관 | 정확도 |
| `entities` | 주문번호, 상품명, 금액, 날짜, 요금제명 등 (업종별 목록) | 값 단위 정밀도·재현율 (정규화 후 완전 일치) |
| `actions_taken` | 상담 중 실제로 한 처리 목록 (정해진 코드) | 집합 F1 |
| `follow_up` | 후속 조치 필요 여부 + 코드 | 정확도 |
| `summary` | 3~5문장 한국어 요약 | 필수 사실 포함률, 틀린 사실 수 |

## 데이터: 명세 먼저 만들고 대화는 그 다음에
공개된 한국어 상담 요약 데이터 중 라이선스가 분명하고 재배포 가능한 것을 찾지 못했다 (2026-09-26 Hugging Face 검색). 그래서 **정답을 먼저 만들고 대화를 나중에 만든다.**

1. **시나리오 명세 생성기** (코드, seed 고정): 업종, 고객 상황, 문의 유형, 핵심 값, 상담원이 한 처리, 결과, 대화 중 일어나는 일(고객이 번호를 잘못 말했다가 고침, 화제 전환, 감정 표현 등)을 뽑는다. **구조화 필드의 정답은 이 명세에서 바로 나온다.** LLM이 정답을 만들지 않는다.
2. **대화 생성**: 로컬 교사 모델(Ollama qwen2.5 14B)에게 명세를 주고 대화를 쓰게 한다.
3. **자동 검사**: 명세의 핵심 값이 대화에 그대로 나오는지, 명세에 없는 번호·금액이 나오지 않는지 코드로 확인하고, 통과하지 못한 대화는 버린다 (버린 비율을 보고한다).
4. **요약 정답**: 명세에서 "요약에 꼭 들어가야 할 사실" 목록을 만든다. 참고용 요약문은 교사가 쓰지만, 채점은 사실 목록으로 한다.

### 업종 (모두 가상)
- 학습·개발·시험: 온라인 쇼핑몰, 통신사, 택배
- **학습에서 뺀 업종** (도메인 차이 시험): 카드·보험 중 하나. 스키마는 같고 유형 목록과 핵심 값 종류만 다르다

### 데이터 나누기
| 세트 | 만드는 방법 | 용도 |
|---|---|---|
| train | 명세 생성기 + 교사 대화 (약 3천~6천 건, 0단계에서 확정) | 학습 |
| dev | 같은 방식, 다른 seed (약 300건) | 후보 고르기, 실패 분석 |
| test-A | 같은 방식, 다른 seed (약 300건) | 단계 끝에 한 번 |
| test-B (생성기 차이) | 같은 명세 형식, **다른 모델 계열이 쓴 대화** 약 60~100건 (Claude가 세션에서 작성. 교사와 말투·구성이 다르게) | 생성기에 맞춰진 것인지 확인 |
| test-C (도메인 차이) | 학습에서 뺀 업종 약 200건 | 새 업종 일반화 |
| test-D (음성 조건) | test-A를 TTS로 읽고 Whisper로 다시 받아 적은 전사 | 인식 오류 강건성 |
| (선택) 실제 상담 | AI Hub 상담 데이터 (사용자가 직접 신청·다운로드) | 실제 대화에서의 확인. 재배포 금지라 건별 결과는 커밋하지 않고 집계만 남긴다 |

명세와 정답이 한 곳에서 나오므로 test 세트의 명세 seed와 train seed는 겹치지 않게 하고, 핵심 값이 같은 대화가 세트를 넘나들지 않는지 테스트로 확인한다.

## 평가 방식
- **형식**: JSON 파싱 성공률, 스키마 통과율. 형식이 틀리면 그 건의 모든 필드를 오답으로 친다 (따로 "형식 제외 점수"도 보고)
- **구조화 필드**: 위 표의 지표. 핵심 값은 숫자·날짜·주문번호 정규화 뒤 완전 일치
- **환각**: 출력한 핵심 값 중 대화 원문에 없는 값의 비율 (코드로 확인. 판정 모델을 쓰지 않는다)
- **요약**: 필수 사실 포함률과 틀린 사실 수를 판정 모델(14B)로 센다. 판정 모델 자체의 신뢰도를 먼저 잰다: dev 50건을 사람 기준(Claude가 사실 목록과 대조해 직접 채점)과 비교해 일치율을 보고하고, 일치율이 낮으면 요약 지표는 참고치로만 쓴다
- **효율**: 건당 지연 시간(p50/p95), 초당 토큰, 최대 GPU 메모리, 모델 파일 크기
- **불확실성**: 건 단위 부트스트랩 95% 구간. 두 후보 비교는 같은 건끼리 짝지은 부트스트랩
- **리포트**: 건마다 입력 id, 출력 원문, 파싱 결과, 필드별 채점을 JSONL로 남겨 다시 계산할 수 있게 한다

## 모델 후보 (초안. 재기 전에 `experiments.md`에 확정)
라이선스는 2026-09-26 Hugging Face 카드 기준으로 모두 Apache-2.0.

| 역할 | 후보 |
|---|---|
| 학생 | Qwen3-1.7B, Qwen3-4B, kanana-1.5-2.1b-instruct (한국어 특화) |
| 비교 기준 (학습 안 함) | 각 학생의 zero-shot·few-shot, qwen2.5 7B·14B instruct (Ollama, 이미 설치) |
| 교사·판정 | qwen2.5 14B instruct (Ollama) |

- 교사와 판정 모델이 같아 생기는 편향: 판정은 사실 목록 대조로 좁히고, 사람 기준 일치율로 확인한다
- 학습 방식: 1.7~2B는 LoRA(fp16), 4B는 QLoRA(4bit). RTX 2080 Ti라 bf16이 없어 fp16 AMP로 학습한다
- 학습 데이터 크기 곡선: 가장 좋은 학생으로 train 500 / 1500 / 전체를 비교해 "데이터가 얼마나 필요한가"를 남긴다

## 서빙
- LoRA를 합친 모델을 GGUF(Q8_0, Q4_K_M)로 바꿔 Ollama에 올리고, JSON 스키마 강제 출력으로 부른다. transformers fp16 추론과 정확도·지연을 비교한다
- FastAPI 서비스: `POST /summarize` (대화 → 기록 JSON), 스키마 검증 실패 시 한 번 재시도하고 그래도 실패하면 실패로 돌려준다, 요청별 지연·토큰 로그. Docker Compose
- 연결 (선택): support-agent의 상담 기록을 이 서비스에 넣어 상담이 끝나면 후처리 기록을 남기는 흐름
- vLLM은 Windows에서 바로 돌지 않아(WSL/Docker 필요) 기본 경로에서 뺀다. 여유가 되면 부하 시험 비교로만 쓴다

## 구조

```
specs/ (명세 생성기, seed) ──> gen/ (교사 대화 생성 + 자동 검사) ──> data/*.jsonl
                                                                    │
train/ (LoRA/QLoRA, peft) <────────────────────────────────────────┤
    │                                                               │
    └──> export/ (병합 → GGUF → Ollama)                              │
                                                                    ▼
eval/ (추론 실행기: transformers / Ollama 공통) ──> 채점 ──> reports/*.jsonl ──> 표
                                                                    
service/ (FastAPI, 스키마 강제)
```

## 스택
- Python 3.11, uv, pydantic 2
- 학습: torch(cu128), transformers, peft, bitsandbytes, (trl은 편하면 쓰고 아니면 직접 루프)
- 추론·서빙: Ollama(GGUF), llama.cpp 변환 도구, FastAPI, Docker Compose
- 음성 조건: MeloTTS + faster-whisper (support-agent 5단계와 같은 구성. whisper-ko-ft에서 학습한 모델을 쓸지는 3단계에서 정한다)
- pytest, ruff, GitHub Actions (GPU·모델 없이 도는 테스트만)

## 알고 시작하는 위험
- **합성 데이터에 맞춘 점수**: 교사가 쓴 대화로 학습하고 같은 교사가 쓴 대화로 재면 점수가 부풀 수 있다. test-B(다른 모델이 쓴 대화)와 test-C(새 업종)를 따로 보고, test-A만 좋고 B·C가 안 좋으면 그대로 결론에 쓴다
- **교사 14B의 한국어 대화 품질**: 명세의 값이 빠지거나 말투가 어색할 수 있다. 자동 검사 통과율과, 무작위 30건을 읽고 센 문제 비율을 보고한다
- **GPU 11GB, bf16 없음**: fp16 학습이 불안정하면(손실 NaN) 학습률·loss scaling을 먼저 보고, 4B QLoRA가 너무 느리면 1.7~2B만으로 결론을 낸다
- **GPU 공유**: 학습은 몇 시간 걸린다. 다른 프로젝트 측정과 동시에 돌리지 않는다. 데스크톱 앱(게임, Wallpaper Engine)이 속도를 절반 가까이 떨어뜨린 적이 있다
- **GGUF 변환 도구**: Qwen3·kanana 구조가 llama.cpp 변환을 지원하는지 0단계에서 확인한다. 안 되면 해당 모델은 transformers 추론만 잰다
- **판정 모델 신뢰도**: 요약 지표는 사람 기준 일치율이 확인된 뒤에만 결론에 쓴다

|---|---|---|
