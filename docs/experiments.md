# 측정 규칙과 결과

재기 전에 규칙을 적고 커밋한다. 규칙을 바꾸면 바꾼 시점과 이유를 이 문서에 남긴다. test 세트(test-a, test-b, test-c, test-d)는 단계가 끝날 때 그 단계에서 고른 것만 한 번 잰다. 실패 분석은 dev로만 한다.

## 공통

- 출력 스키마: `src/call_summary/schema.py`의 `AfterCallRecord`. 프롬프트: `src/call_summary/prompts.py` (`PROMPT_VERSION`과 해시가 실행 기록마다 남는다)
- 정답: 명세 생성기(`specs.py`)에서만 나온다. 핵심 값은 `values.py`로 정규화해 비교한다
- 구조 필드 지표 (`scoring.py`, 판정 모델 없음)
  - `schema`: 스키마 통과율. 통과하지 못한 건은 모든 필드를 오답으로 친다
  - `exact`: 구조 필드(유형, 결과, 핵심 값, 처리, 후속 조치)가 모두 맞은 비율. **주 지표**
  - `category_acc`, `category_macro_f1`, `resolution_acc`, `follow_up_acc`
  - `entity_p`/`entity_r`/`entity_f1`: (유형, 정규화 값) 단위, 여러 건을 합쳐 계산
  - `hallucination`: 출력한 핵심 값 중 대화 원문 어디에도 없는 값의 비율
  - `action_f1`, `off_list`(허용 목록 밖 라벨을 하나라도 쓴 건의 비율)
- 불확실성: 건 단위 부트스트랩 95% 구간 (2,000회). 두 모델 비교는 같은 건끼리 짝지은 부트스트랩으로 차이의 구간을 낸다
- 디코딩: 모든 모델 탐욕적(temperature 0). Qwen3 계열은 생각 모드를 끈다
- 실행 기록: `reports/<run_id>/` (manifest, 건별 출력·채점, 요약). 공식 측정은 `--official`로 깨끗한 작업 트리에서만 돈다

## 1단계: 데이터 만들기

### 규칙 (2026-09-26, 생성 전)
- 교사: qwen2.5 14B instruct (아래 "파일럿"으로 정함). 생성 설정: `gen.py` `WRITER_VERSION`, temperature 0.8 (요약은 0.3), 명세마다 고정 seed, 대화·요약 각각 최대 3번 시도
- 크기 (업종당): train 500, dev 80, test-a 100 (쇼핑몰·통신·택배 세 업종). test-c: 카드 200. test-b: 업종당 20, 모두 60
  - 처음 초안은 train 700이었다. 파일럿에서 14B가 받아들인 대화 한 건에 약 61초가 걸려 train을 500으로 줄였다 (전체 약 2,240건, 약 38시간)
  - 명세는 목표보다 20% 더 만들고, 업종마다 번호 순서로 자동 검사를 통과한 앞의 N건을 쓴다. 버린 비율을 유형별로 보고한다
- 자동 검사 (`check_dialogue`, `check_summary`): 명세의 값이 글자 그대로 모두 나옴, 말실수 값이 나옴, 명세에 없는 금액·날짜·시각·번호가 없음, 화자 형식, 12~24턴 지시(허용 8~40턴), 요약이 모든 핵심 값을 담고 고치기 전 값을 담지 않음
- 사람 점검: train에서 무작위 30건(seed 0)을 Claude가 읽고 다음을 센다. (1) 명세와 어긋나는 내용 (2) 명세에 없는 처리를 했다고 말함 (3) 결과가 대화에서 드러나지 않음 (4) 어색해서 실제 상담으로 보기 어려움. (1)~(3)이 합쳐 20%를 넘으면 생성 지시문을 고치고 다시 만든다 (그 경우 고친 내용을 여기에 적는다)
- test-b: 같은 명세 형식(`test-b` 분할의 명세)으로 Claude가 대화를 직접 쓴다. 교사와 다른 말투가 되도록 교사 출력을 보고 따라 쓰지 않는다. 같은 자동 검사를 통과해야 한다. 요약 참고문도 Claude가 쓴다
- 겹침 확인: test 세트의 핵심 값(번호)이 train에 나오면 그 건을 뺀다 (테스트로 확인)

### 파일럿 (2026-09-26)
dev 분할 명세 12건(업종당 4건)을 같은 지시문(w1)으로 두 교사에게 만들게 했다. 파일럿 대화는 데이터에 넣지 않는다.

| 교사 | 통과 | 명세 한 건에 걸린 시간 | 거절 이유 |
|---|---|---|---|
| qwen2.5 14B | 10/12 | 51초 | 명세에 없는 금액 1, 턴 수 부족 1 |
| qwen2.5 7B | 7/12 | 19초 | 명세에 없는 금액 2, 요약이 핵심 값 누락 2, 턴 수 부족 1 |

- 통과한 대화를 읽어 보니 7B는 앞뒤가 맞지 않는 내용이 많았다 (예: "주문한 지 3일이 지나 7일 반품 기한이 지났다"). 14B는 대체로 자연스러웠지만 1건에서 상담원 발화 한 턴이 중국어로 바뀌었다 → 한자·가나가 나오면 버리는 검사를 추가했다 (`e98336e`)
- 받아들인 대화 한 건에 드는 시간은 14B 약 61초, 7B 약 33초. 데이터 품질이 test-b·c 결론을 좌우하므로 14B를 쓴다
- 파일럿 대화를 읽다가 명세 생성기의 어색한 값도 찾았다: 택배 요금·데이터 충전·부가서비스 월 요금·적립금·카드 한도·연회비가 해당 유형의 넓은 금액 범위에서 뽑혀 "택배비 128만 원" 같은 값이 나왔고, 배송 지연의 새 도착일과 기사 방문일이 처음 날짜보다 앞설 수 있었다. 슬롯별 값 범위와 날짜 순서를 넣고(`56e691a`, `35a961a`) 명세를 모두 다시 만든 뒤 생성을 시작했다
- 첫 파일럿(주문번호 `915-4821-33` 형식)에서는 14B가 번호를 줄여 말해 9건 중 6건이 거절됐다. 주문번호를 `D` + 7자리로 바꾸고, 긴 번호의 앞부분만 말하는 것은 새 번호로 치지 않게 검사를 고친 뒤 위 파일럿을 다시 했다

## 2단계: 기준선 (초안. 2단계 시작 전에 확정)
- 후보: qwen2.5 1.5B·7B·14B instruct (Ollama, 0-shot), Qwen3-1.7B, Qwen3-4B (transformers fp16, 0-shot과 2-shot)
- 7B는 JSON 스키마 강제 디코딩을 켠 것도 따로 잰다 (형식 문제와 내용 문제를 나눠 보기 위해)
- 요약 판정: 판정 모델(qwen2.5 14B)이 요약과 명세의 사실 목록을 비교해 사실마다 포함/누락/틀림을 매긴다. dev 50건을 Claude가 같은 기준으로 채점하고 판정 모델과의 일치율(사실 단위)을 보고한다. 일치율이 0.8 미만이면 요약 지표는 참고치로만 쓴다
- test-a는 2단계 끝에 학습 전 학생(가장 좋은 것), 7B, 14B만 한 번 잰다

## 3단계: 학습 (초안. 3단계 시작 전에 확정)
- 학생 후보: Qwen3-1.7B (LoRA, fp16), Qwen3-4B (QLoRA 4bit)
- 손실은 답(JSON) 부분만 계산한다. LoRA r=16, alpha=32, dropout 0.05, 모든 선형층, 학습률 2e-4 코사인, 2 epoch를 기본으로 하고 dev에서 고른다
- 고르는 기준: dev `exact`, 같으면 `entity_f1`, 그다음 `hallucination`이 낮은 것
- 판정 문장 (test-a·b·c, 짝지은 부트스트랩 95% 구간):
  - "학습 효과 있음": 학습한 학생 − 학습 전 같은 학생의 `exact` 차이 하한 > 0
  - "7B를 넘음"/"14B를 넘음": 학습한 학생 − 해당 모델의 `exact` 차이 하한 > 0. 상한 < 0이면 "못 미침", 그 사이면 "구분 안 됨"
  - test-b·c에서 "학습 효과 있음"이 아니면 "생성기(또는 업종)에 맞춰진 이득"으로 적는다
- 데이터 크기 곡선: 고른 학생으로 train 500 / 1,500 / 전체를 같은 설정으로 학습해 dev에서 비교한다
