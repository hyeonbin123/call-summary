# 측정 규칙과 결과

재기 전에 규칙을 적고 커밋한다. 규칙을 바꾸면 바꾼 시점과 이유를 이 문서에 남긴다. test 세트(test-a, test-b, test-c, test-d)는 단계가 끝날 때 그 단계에서 고른 것만 한 번 잰다. 실패 분석은 dev로만 한다.

## 공통

- 출력 스키마: `src/call_summary/schema.py`의 `AfterCallRecord`. 프롬프트: `src/call_summary/prompts.py` (`PROMPT_VERSION`과 해시가 실행 기록마다 남는다)
- 정답: 명세 생성기(`specs.py`)에서만 나온다. 핵심 값은 `values.py`로 정규화해 비교한다
- 구조 필드 지표 (`scoring.py`, 판정 모델 없음)
  - `schema`: 스키마 통과율. 통과하지 못한 건은 모든 필드를 오답으로 친다
  - `exact`: 구조 필드(유형, 결과, 핵심 값, 처리, 후속 조치)가 모두 맞은 비율. **주 지표**
  - `category_acc`, `category_macro_f1`, `resolution_acc`, `follow_up_acc`
  - `entity_p`/`entity_r`/`entity_f1`: (유형, 정규화 값) 단위, 여러 건을 합쳐 계산
  - `hallucination`: 출력한 핵심 값 중 대화 원문 어디에도 없는 값의 비율
  - `action_f1`, `off_list`(허용 목록 밖 라벨을 하나라도 쓴 건의 비율)
- 불확실성: 건 단위 부트스트랩 95% 구간 (2,000회). 두 모델 비교는 같은 건끼리 짝지은 부트스트랩으로 차이의 구간을 낸다
- 디코딩: 모든 모델 탐욕적(temperature 0). Qwen3 계열은 생각 모드를 끈다
- 실행 기록: `reports/<run_id>/` (manifest, 건별 출력·채점, 요약). 공식 측정은 `--official`로 깨끗한 작업 트리에서만 돈다

- 크기 (업종당): train 500, dev 80, test-a 100 (쇼핑몰·통신·택배 세 업종). test-c: 카드 200. test-b: 업종당 20, 모두 60
  - 처음 초안은 train 700이었다. 파일럿에서 14B가 받아들인 대화 한 건에 약 61초가 걸려 train을 500으로 줄였다 (전체 약 2,240건, 약 38시간)

- 자동 검사 (`check_dialogue`, `check_summary`): 명세의 값이 글자 그대로 모두 나옴, 말실수 값이 나옴, 명세에 없는 금액·날짜·시각·번호가 없음, 화자 형식, 12~24턴 지시(허용 8~40턴), 요약이 모든 핵심 값을 담고 고치기 전 값을 담지 않음
- 사람 점검: train에서 무작위 30건(seed 0)을 Claude가 읽고 다음을 센다. (1) 명세와 어긋나는 내용 (2) 명세에 없는 처리를 했다고 말함 (3) 결과가 대화에서 드러나지 않음 (4) 어색해서 실제 상담으로 보기 어려움. (1)~(3)이 합쳐 20%를 넘으면 생성 지시문을 고치고 다시 만든다 (그 경우 고친 내용을 여기에 적는다)
- test-b: 같은 명세 형식(`test-b` 분할의 명세)으로 Claude가 대화를 직접 쓴다. 교사와 다른 말투가 되도록 교사 출력을 보고 따라 쓰지 않는다. 같은 자동 검사를 통과해야 한다. 요약 참고문도 Claude가 쓴다
- 겹침 확인: test 세트의 핵심 값(번호)이 train에 나오면 그 건을 뺀다 (테스트로 확인)

- **test-c의 한계**: 학습한 학생이 test-c에서 틀린 90건 중 61건이 처리 라벨 오류다. 다른 업종에서 배운 비슷한 라벨을 쓰거나('청구 내역 조회' 대신 '결제 내역 확인' 15건, 부정 사용에 '분실 신고' 18건), 카드 업종에만 있는 처리를 빠뜨린다('연회비 면제 신청' 10건, '연회비 조회' 8건). 새 업종의 라벨 목록은 프롬프트에만 있고 학습 데이터에는 없으므로, 새 업종을 붙이려면 그 업종의 학습 예시가 필요하다는 뜻이다 (test 결과는 설명에만 쓰고, 이것을 보고 모델·규칙을 고치지 않았다)
- 환각: 사전에 정한 정의는 "대화에 없는 값"이라 빈 값 채우기(`""`)도 포함한다. test-c에서 14B의 환각 123건 중 80건이 빈 값이라 두 수치를 함께 적는다. 빈 값을 빼도 14B 9.8%, 학습한 학생 1.5%
- p2(기록 기준을 적은 프롬프트)는 14B의 exact를 test-a +3.0, test-b +3.3, test-c +9.0 올렸다. 관례를 글로 적으면 조금 나아지지만 학습과는 거리가 멀다
- 학습 전 비교는 fp16 바탕, 학습한 학생은 4bit 바탕이라 학습한 쪽에 불리한 조건이다

**데이터 크기 곡선 (dev, 같은 설정)**

| 학습 건수 | exact | 핵심 값 F1 | 후속 조치 | 학습 시간 |
|---|---|---|---|---|
| 500 (업종당 약 167) | 66.2 [60.0, 72.1] | 96.6 | 82.1 | 35분 |
| 1,500 | 93.3 [90.0, 96.2] | 99.3 | 98.3 | 2시간 25분 |

500건만으로도 학습 전(18.3)과 14B(25.0)를 크게 넘지만, 1,500건까지 늘리면 exact가 27%p 더 오른다. 곡선이 아직 평평해지지 않았다

**지연**: 표의 p50 지연은 4bit transformers(배치 4의 벽시계를 건수로 나눔, 건당 약 8~9초)와 Ollama(14B 약 10~13초)가 섞여 있다. 같은 조건의 서빙 지연은 5단계에서 잰다

## 4단계: 음성 인식 오류 조건 (2026-09-29 규칙, 측정 전)

### 조건
- 대화의 발화마다 `scripts/asr_condition.py`로 음성 조건 전사를 만든다: 발음형으로 풀어 쓰기(support-agent의 `verbalize`) → MeloTTS 한국어(목소리 하나, 상담원 속도 1.0·고객 1.1, 발화마다 고정 seed) → 전화 채널(300~3400 Hz 대역, 8 kHz, 8비트 μ-law, whisper-ko-ft와 같은 식) → faster-whisper large-v3-turbo(한국어, beam 5, temperature 0). 음성 합성·인식 모델이 transformers 4.27을 요구해 support-agent의 음성 환경에서 돌리고, 버전은 각 건의 `meta.asr`에 남긴다
- 발화 단위로 따로 인식하므로 화자 분리는 완벽하다고 가정한다. 잡음·끼어들기·실제 사람 목소리는 없다 (한계)
- **test-d** = test-a 300건의 음성 조건판, **dev-asr** = dev 240건의 음성 조건판, **train-half-asr** = train에서 업종마다 짝수 번째인 750건의 음성 조건판. 정답(명세)과 참고 요약은 원래 것 그대로다

### 채점
- exact와 필드 지표는 그대로다 (정답 값과 정규화 규칙 동일)
- 환각 검사만 음성 조건에서 번호를 더 넓게 찾는다: 인식기가 "5533-8050-3287"을 "5,533, 8,050에서 3,287"처럼 적는 일이 있어, 전사에서 숫자 덩어리 사이의 다른 글자가 3자 이하이면 한 덩어리로 이어 읽고, 예측한 번호의 숫자(4자리 이상)가 그 안에 있으면 전사에 있는 값으로 본다 (`values.occurs_in_transcript(spoken=True)`). 이 변경으로 지금까지의 모든 실행(6,160건)을 다시 채점해 달라지는 것이 없음을 확인했다
- **값 보존율**: 정답 핵심 값 중 음성 전사에서 (같은 규칙으로) 찾을 수 있는 비율을 유형별로 보고한다. 모델이 전사를 그대로 옮겨 적어 맞힐 수 있는 상한에 가깝다

- **복원과 환각을 나눠 센다** (2026-09-29 추가, 모델을 재기 전): 학습한 학생은 학습 데이터에서 본 상품·기기 이름으로 인식 오류를 바로잡을 수 있다("은하택구" → "은하 탭 9"). 이 경우 값은 전사에 없으므로 환각 지표에 들어간다. 음성 조건에서는 예측한 핵심 값 중 전사에 없는 것을 다시 "정답과 같은 값(복원)"과 "정답에도 없는 값(지어낸 값)"으로 나눠 보고한다

### 판정 (주 지표 exact, 같은 300건끼리 짝지은 부트스트랩 95% 구간)
- "음성 조건에서 떨어짐": 깨끗한 학생의 test-d − test-a 상한 < 0
- "섞어 학습이 음성 조건에서 나음": 섞어 학습한 학생 − 깨끗한 학생, test-d에서 하한 > 0
- "깨끗한 전사에서 손해 없음": 섞어 학습한 학생 − 깨끗한 학생, test-a에서 하한 > −3%p (비열등 한계 3%p)
- "음성 조건에서도 14B를 넘음": 고른 학생(섞어 학습한 학생이 위 두 판정을 모두 통과하면 그것, 아니면 깨끗한 학생) − 14B, test-d에서 하한 > 0

## 5단계: 서빙 (2026-09-29 규칙 초안. 5단계를 재기 전에 확정)

### 내보내기
- 3단계에서 고른 학생(4단계에서 섞어 학습한 학생이 판정을 모두 통과하면 그것)의 어댑터를 fp16 바탕 모델에 합친다 → llama.cpp로 GGUF f16 → Ollama에서 q8_0, q4_K_M으로 양자화 (`call_summary.export`)
- QLoRA 어댑터는 4bit 바탕 위에서 학습했으므로 fp16에 합친 모델은 평가한 모델과 똑같지 않다. HF(4bit + 어댑터)와 GGUF f16의 차이를 "합치기 + 실행기 차이"로 따로 보고한다

### 양자화 손실 (dev 240건, p1, 0-shot, 스키마 강제 없음)

- 함께 적는 것: 모델 파일 크기, Ollama가 보고하는 VRAM, 순차 요청 지연 p50/p95
