# 측정 규칙과 결과

재기 전에 규칙을 적고 커밋한다. 규칙을 바꾸면 바꾼 시점과 이유를 이 문서에 남긴다. test 세트(test-a, test-b, test-c, test-d)는 단계가 끝날 때 그 단계에서 고른 것만 한 번 잰다. 실패 분석은 dev로만 한다.

## 공통

- 출력 스키마: `src/call_summary/schema.py`의 `AfterCallRecord`. 프롬프트: `src/call_summary/prompts.py` (`PROMPT_VERSION`과 해시가 실행 기록마다 남는다)
- 정답: 명세 생성기(`specs.py`)에서만 나온다. 핵심 값은 `values.py`로 정규화해 비교한다
- 구조 필드 지표 (`scoring.py`, 판정 모델 없음)
  - `schema`: 스키마 통과율. 통과하지 못한 건은 모든 필드를 오답으로 친다
  - `exact`: 구조 필드(유형, 결과, 핵심 값, 처리, 후속 조치)가 모두 맞은 비율. **주 지표**
  - `category_acc`, `category_macro_f1`, `resolution_acc`, `follow_up_acc`
  - `entity_p`/`entity_r`/`entity_f1`: (유형, 정규화 값) 단위, 여러 건을 합쳐 계산
  - `hallucination`: 출력한 핵심 값 중 대화 원문 어디에도 없는 값의 비율
  - `action_f1`, `off_list`(허용 목록 밖 라벨을 하나라도 쓴 건의 비율)
- 불확실성: 건 단위 부트스트랩 95% 구간 (2,000회). 두 모델 비교는 같은 건끼리 짝지은 부트스트랩으로 차이의 구간을 낸다
- 디코딩: 모든 모델 탐욕적(temperature 0). Qwen3 계열은 생각 모드를 끈다
- 실행 기록: `reports/<run_id>/` (manifest, 건별 출력·채점, 요약). 공식 측정은 `--official`로 깨끗한 작업 트리에서만 돈다

## 계획과 달라진 것
- 2026-09-26 kanana-1.5-2.1b-instruct를 학생 후보에서 뺐다. 이 모델의 설정(hidden 1792, 어텐션 헤드 24, head_dim 128)을 transformers 5.17의 설정 검사가 "hidden size가 헤드 수의 배수가 아니다"로 거부해 불러올 수 없고, llama.cpp 변환 스크립트도 같은 검사로 멈춘다. 우회(검사 끄기, transformers 4.x 별도 환경)는 측정 조건을 흔들어 쓰지 않았다 (`a1d09a6`에서 이 절에 적었는데, 2026-09-28 2단계 결과를 넣을 때(`7ef72c6`) 실수로 지워져 2026-10-03 다시 적는다)
- 4단계 음성 조건의 인식기는 whisper-ko-ft에서 학습한 모델이 아니라 학습하지 않은 faster-whisper `large-v3-turbo`다 (support-agent 음성 채널과 같은 설정). 계획은 "whisper-ko-ft 모델을 쓸지는 3단계에서 정한다"였는데, 4단계 규칙(`1c9dfca`)에 고른 이유를 적지 않았다. 2026-10-03 확인한 사실: (1) whisper-ko-ft의 학습 모델은 Zeroth-Korean 낭독 음성으로 학습한 것이고(small 전체 파인튜닝, turbo LoRA), 2·3단계 모델은 다른 한국어 도메인(FLEURS)에서 나빠진다는 판정("도메인 전용")을 받았다. 숫자 표기를 바꿔 다시 학습한 6단계 모델만 범용 판정을 받았다 (2) 그 6단계 모델을 faster-whisper(CTranslate2)로 돌린 유일한 시도(2026-09-20)는 멜 필터 수가 맞지 않아 모든 발화에서 실패했고, whisper-ko-ft에서 이 문제를 고친 것은 2026-10-02(`61b4b2f`)다. 4단계를 정한 2026-09-29에는 이 프로젝트의 음성 환경(faster-whisper)에서 돌릴 수 있는 학습 모델이 없었다 (3) 학습하지 않은 범용 인식기를 쓰면 결과가 "상용 인식기를 그대로 붙인 경우"에 가깝고 support-agent의 음성 조건과 비교할 수 있다. 학습한 인식기(상담 통화가 아닌 낭독 음성으로 학습)로 바꿨을 때 4단계 결과가 어떻게 달라지는지는 재지 않았다
- 2026-10-03 음성 조건을 v2로 고친다: 4단계 조건이 운송장번호를 기수와 범위의 '에서'로 읽어 합성했다 (측정 인공물). 규칙은 맨 아래 "음성 조건 v2" 절, v1 결과는 그대로 둔다

- 판정 문장 (짝지은 부트스트랩 95% 구간, 주 지표 `exact`)

  - "7B를 넘음"/"14B를 넘음": 학습한 학생 − 해당 모델의 차이 하한 > 0. 상한 < 0이면 "못 미침", 그 사이면 "구분 안 됨"
  - "관례를 적은 프롬프트보다 나음": 학습한 학생 − 14B-p2의 차이 하한 > 0 (14B-p2를 test에서 잰 경우에만)
  - test-b·c에서 "학습 효과 있음"이 아니면 "생성기(또는 업종)에 맞춰진 이득"으로 적는다

## 4단계: 음성 인식 오류 조건 (2026-09-29 규칙, 측정 전)

### 조건
- 대화의 발화마다 `scripts/asr_condition.py`로 음성 조건 전사를 만든다: 발음형으로 풀어 쓰기(support-agent의 `verbalize`) → MeloTTS 한국어(목소리 하나, 상담원 속도 1.0·고객 1.1, 발화마다 고정 seed) → 전화 채널(300~3400 Hz 대역, 8 kHz, 8비트 μ-law, whisper-ko-ft와 같은 식) → faster-whisper large-v3-turbo(한국어, beam 5, temperature 0). 음성 합성·인식 모델이 transformers 4.27을 요구해 support-agent의 음성 환경에서 돌리고, 버전은 각 건의 `meta.asr`에 남긴다

## 5단계: 서빙 (초안 2026-09-29, 아래 "확정"으로 2026-09-29 밤 측정 전에 확정)

### 내보내기

### 왜 다시 재나

- 영향: 4단계 섞어 학습한 학생이 test-d에서 놓친 정답 값 55개 중 15개, 서빙 q8_0이 dev-asr에서 놓친 40개 중 13개가 운송장번호다. 섞어 학습한 학생의 학습 데이터(train-half-asr)도 이 읽기로 만들어졌다

### 조건 v2 (이것만 바꾼다)
- `scripts/asr_condition.py --verbalizer v2`: 발화를 `verbalize`에 넘기기 전에, NFKC로 정규화한 글에서 운송장번호 꼴 `(?<![\d-])\d{4}-\d{4}-\d{4}(?![\d-])`만 숫자 하나씩(0은 "공") 읽고 묶음 사이에 쉼표를 둔다: "6291-7877-5168로" → "육이구일, 칠팔칠칠, 오일육팔 로". `verbalize`가 전화번호를 읽는 방식과 같다. 이 꼴이 없는 발화는 글자 하나 바꾸지 않고 v1과 똑같이 `verbalize`에 넘긴다 (`tests/test_asr_condition.py`)
- support-agent는 고치지 않는다. 합성 음성·목소리·속도, 발화별 seed, 전화 채널, 인식기, 정답, 채점(`spoken=True` 규칙 포함)은 v1 그대로다. 인식기가 v2 번호를 한글 숫자 이름("오오삼삼")으로 적으면 채점 규칙상 "남지 않음"으로 센다 (규칙을 바꾸지 않는다)
- 남는 것: train 절반의 주소 한 발화("역삼동 761-4 입니다")는 여전히 범위로 읽힌다 (dev·test에는 없음). 운송장번호 꼴이 아닌 하이픈 숫자는 이 규칙의 범위 밖이다. 같은 범위 규칙 오발동은 support-agent 음성 채널의 하이픈 숫자 번호에도 생기므로 그 저장소에 따로 넘긴다 (여기서는 고치지 않는다)
- 캐시와 음성 환경 확인 (2026-10-03, CPU만, 모델을 올리지 않음): 지금의 음성 환경(melotts 0.1.2, torch 2.11.0+cu128, faster-whisper 1.2.1, ctranslate2 4.8.2)과 지금의 `verbalize`로 v1 16,663발화의 캐시 키를 다시 계산하면 모두 캐시에 있다. 고친 스크립트를 v1로 캐시만으로 다시 돌리면 `datasets/dev-asr.jsonl`·`test-d.jsonl`과 건마다 같다 (`meta.asr.verbalizer` 필드만 더해짐). v2의 계획(`--dry-run`): 새로 합성·인식할 발화 dev 142, test-a 185, train 절반 485, 나머지는 캐시를 그대로 쓴다. 스크립트는 v1과 같게 읽는 발화가 캐시에 없으면(음성 환경이 바뀐 것) 멈춘다 (`--allow-full-run` 없이는)
- 파일: `datasets/dev-asr-v2.jsonl`, `datasets/test-d-v2.jsonl`, `datasets/train-half-asr-v2.jsonl`. 분할 이름은 v1과 같고(`dev-asr` 등) 각 건의 `meta.asr.verbalizer`가 `v2`다. v1 파일은 그대로 둔다. 섞어 학습용 `data/train_mixed_v2.jsonl`은 4단계와 같은 방식(train에서 업종마다 짝수 번째 750건을 v2 음성 조건판으로 바꿈)

### 입력 분석 (모델을 돌리기 전에 적는다)
- `python -m call_summary.asr_report survival`로 dev-asr·test-d의 v1과 v2에서 유형별 값 보존율과 모든 값이 남은 건의 비율. 이 도구로 4단계 입력 분석을 다시 계산하면 적힌 값(test-d 83.7%, dev-asr 79.6%, 운송장번호 90.8%, 주문번호 84.2% 등)이 그대로 나온다
- v2 운송장번호를 인식기가 어떻게 적었는지(숫자, 쉼표·공백으로 나뉜 숫자, 한글 숫자 이름 등)를 dev-asr에서 세어 함께 적는다

### 측정 조건
- Ollama 0.35.1 (자동 업데이트 끔, 2026-10-03). 4·5단계의 Ollama 수치(0.34.2, 0.35.0)와 조건이 다르므로 같은 조건의 기준을 이 단계 안에서 다시 잰다. 실행 기록 manifest에 모델 digest와 Ollama 버전이 남는다 (`model_fingerprint`, 버전은 이번에 추가)
- 모델은 모두 Ollama에서 서비스와 같은 설정으로 잰다: `evaluate --backend ollama`, p1 0-shot, num_ctx 4096, 스키마 강제 없음, temperature 0. 정확도만 재므로 유휴 대기는 하지 않고, 잴 때 GPU를 함께 쓴 프로그램을 적는다

### 후보와 고르는 규칙 (주 지표 exact, 같은 건끼리 짝지은 부트스트랩 95% 구간)
- **R** (같은 조건의 기준): 서빙 중인 섞어 학습한 학생 `call-summary-4b-dq:q8_0`을 dev-asr(v1)에서 다시 잰다
- **A**: 같은 모델을 dev-asr-v2에서 잰다. A − R(같은 모델, 같은 240건, 입력만 v1 → v2)이 조건 변경만의 효과다
- **B를 학습할지**: A의 exact가 R보다 3%p 넘게 낮을 때만(점 추정 A − R < −3.0%p) B를 학습한다. 아니면 B 없이 A로 간다
- **B**: 4단계 섞어 학습과 같은 설정(Qwen3-4B QLoRA r16, alpha 32, lr 2e-4, 2 epoch = 188 스텝, seed 0)을 `data/train_mixed_v2.jsonl`로 학습하고 마지막(2 epoch) 어댑터를 쓴다 (스텝 수를 같게 두려고 epoch은 고르지 않는다). 5단계와 같은 방식(4bit 바탕을 풀어 합침 → GGUF f16 → llama-quantize q8_0)으로 `call-summary-4b-v2-dq:q8_0`을 만든다. B를 학습하면 B를 dev-asr-v2와 dev에서, A를 dev에서도 잰다 (0.35.1에서 짝을 맞추려고)
- **B를 고르는 조건**: (1) dev-asr-v2에서 B − A의 하한 > 0, (2) dev에서 B − A의 하한 > −3%p (글 전사에서 손해 없음). 둘 다 맞으면 B, 아니면 A

### test (고른 것만 한 번)
- 고른 모델로 **test-d-v2**를 한 번 잰다 (`--official --allow-test`). 적을 것: exact [95% 구간], 핵심 값 F1, 전사에 없는 값과 그 안의 복원/지어낸 값(`asr_report unfound`, 4단계와 같은 구분), 유형별 놓친 값 수
- 4단계 test-d 80.7(v1, HF 4bit + 어댑터)과 나란히 적는다. 실행기(HF 4bit → Ollama q8_0)와 입력(v1 → v2)이 함께 바뀌었으므로 두 수의 차이를 조건 변경만의 효과로 읽지 않는다. 그 효과는 dev-asr의 A − R로 본다. 같은 300건의 짝지은 차이도 참고로 적는다
- B를 고르면 B가 새 서빙 모델이 되므로 test-a에서도 한 번 잰다 (글 전사)
- 결과의 방향과 상관없이 v2가 앞으로 보고하는 음성 조건이다. README의 음성 조건 수치는 v2로 바꾸고 v1 수치를 함께 적는다
